# 小人儿保险 AI Agent 项目｜面试讲解指南

> 用途：用于 AI 售前解决方案顾问、AI 应用解决方案、Agent/RAG 应用开发等岗位的项目介绍与技术面试。
>
> 说明：本文根据仓库当前公开源码和项目技术文档整理。请把“已实现”“已验证”和“尚未验证”区分开来，不要把本地演示包装成已上线的商业系统。

## 一、项目定位：先用一句话讲清楚

**小人儿保险是一个面向保险资料检索与业务分析场景的 AI Agent 演示平台，将客户需求结构化、私有知识库检索、工具编排、原文证据核验和 Word/PDF 报告交付串成可观察、可追溯的工作流。**

它不是单纯的聊天机器人，也不是实际承保或投保系统。项目重点是展示如何把大模型能力放进有边界、有证据、有状态、可检查的业务流程。

## 二、90 秒项目介绍（建议熟练掌握）

> 我做的项目叫“小人儿保险”，它是一个面向保险资料检索和业务分析场景的 AI Agent 演示平台。
>
> 它解决的不是简单问答，而是把一段客户自然语言需求，逐步转成结构化信息，再结合本地知识库检索保险资料，通过 Agent 工作流完成资料核验、字段整理和报告生成。
>
> 技术上，项目使用 Next.js、React 和 TypeScript 构建前后端；复杂任务使用 LangGraph StateGraph 管理节点状态和条件路由；RAG 部分使用 multilingual-e5-small 本地 Embedding，把文档、版本、切片和向量保存在 SQLite 中；模型通过服务端适配 DeepSeek API。
>
> 我比较重视结果的可追溯性：检索结果要能对应到真实文档、版本和页码；资料缺失或内容冲突时，系统会标记待核实或资料不足，而不是让模型凭常识补全。项目还包含数据中台和评测中台，用来观察数据版本、检索和 Agent 运行过程。
>
> 当前项目以本地单用户演示为主。公开包的自动化测试通过了 337 项，Playwright 桌面和移动端测试通过了 132 项；但这不等于真实付费模型的完整业务质量已经验收，公网多租户部署也还需要进一步建设。

**讲述节奏：**

- 前 15 秒：项目是什么、解决什么业务问题。
- 中间 45 秒：讲清楚 LangGraph、RAG、模型和数据如何配合。
- 最后 30 秒：强调证据追溯、质量边界、测试结果和当前限制。

## 四、系统架构：面试官问“整体怎么设计”时

### 1. 分层说明

| 层次 | 当前方案 | 主要职责 |
| --- | --- | --- |
| 前端展示层 | Next.js App Router、React 19、TypeScript、Tailwind CSS、shadcn/ui | 页面、表单、结果展示、图表和交互 |
| 服务端 API 层 | Next.js 同源 API、Zod 校验 | 接收请求、校验输入、执行本机访问边界、管理取消与响应 |
| Agent 编排层 | LangGraph.js StateGraph、LangChain Core | 节点状态、条件路由、工具调用、超时、有限重试和终态 |
| RAG 检索层 | Transformers.js、本地 multilingual-e5-small、SQLite | 文档解析、切片、向量生成、检索与来源定位 |
| 模型层 | 服务端 DeepSeek API 适配 | 在明确授权和配置下调用模型，密钥留在服务端 |
| 业务交付层 | 需求分析、产品字段对比、报告生成 | 把需求、证据和未知项组织为结构化结果 |
| 数据与评测层 | 独立 SQLite 数据库、数据中台、评测中台 | 数据版本、质量、运行观测、检索评测与人工复核 |

### 2. 业务主流程

```mermaid
flowchart LR
    A[客户自然语言需求] --> B[输入校验与需求结构化]
    B --> C[提取明确需求和信息缺口]
    C --> D[生成检索计划]
    D --> E[本地知识库检索]
    E --> F[当前文档与版本核验]
    F --> G[字段提取与证据关联]
    G --> H[结构化分析报告]
    H --> I[Word / PDF 导出]
    F -->|资料不足或冲突| J[标记待核实 / 无法确认]
    J --> H
```

### 3. Agent 工作流

客户需求分析 Agent 的实际工作流为：

```text
输入校验
→ 客户信息结构化
→ 明确需求提取
→ 待客户确认的沟通优先级
→ 信息缺口和追问
→ 检索计划
→ knowledge_search
→ 当前原文和版本检查
→ 逐资料字段提取
→ 责任字面关联和未知项
→ 报告
→ Word / PDF
```

面试时强调：

- LangGraph 管理的是有状态的多步骤工作流，不是简单地把多个提示词串起来。
- 每个节点完成什么任务、何时走哪条分支，都有明确的状态和条件。
- 没有明确需求时可以跳过检索；没有证据时跳过产品字段提取。
- 节点和工具的开始、完成、失败、取消事件来自实际执行，不用假进度代替。
- 有限重试、图步数和请求时间受到约束；取消后不再启动后续工具。
- 当前没有把它描述成跨进程自动恢复的持久任务队列。

## 五、核心技术深挖

### 1. RAG 是怎么实现的？

可以按“文档处理—索引—检索—证据核验—生成”五步回答：

1. **文档处理**：支持 PDF、DOCX、TXT、Markdown 等资料解析，并保留文档和页码关联。
2. **切片与向量化**：按内容边界切片，使用本地 `multilingual-e5-small` 生成 384 维归一化 Embedding。
3. **存储**：文档、版本、切片和向量等数据保存在本地 SQLite。
4. **检索**：通过向量召回，并在客户需求分析入口结合受限关键词/文件名候选；候选融合、去重后再检查文档当前版本和有效状态。
5. **证据输出**：模型只能把检索内容作为参考资料；结果保留文档、版本、页码和片段。没有足够依据时标记资料不足或待核实。

**回答重点：** 向量相似度只用于召回候选，不代表保险责任成立，也不代表产品适合客户。

### 2. 为什么检索还要结合关键词？

项目曾遇到一个实际问题：客户明确写出产品名称时，如果只把类别模板交给向量检索，可能丢失原需求中的产品名称；一些宽泛责任词也可能低于已有向量阈值。

处理方式是：

- 保留客户明确提出的完整需求。
- 用受限查询计划复用原向量检索。
- 增加实际文档名、责任词和字段词的关键词候选。
- 两路候选进行排名融合和去重。
- 关键词候选不伪造余弦分数，也不降低共享向量检索阈值。
- 最终仍重新核验文档有效状态和当前版本。

**注意：** 关键词命中只代表候选资料，不等于证明保险责任或客户适用性。

### 3. 如何控制幻觉和错误结论？

项目不是只依赖 Prompt 告诉模型“不要幻觉”，而是从数据和流程上增加约束：

- 事实字段必须关联真实资料原文、版本和页码。
- 产品正式名称、保险公司等身份信息必须有明确原文依据，不能从文件名或品牌前缀推断。
- 对字段保留已找到、未找到、无法确认等状态。
- 不同资料之间出现冲突时保留不同原文及出处，不擅自选择一方。
- 缺失资料不代表责任不存在，不能用常识补齐。
- 报告导出前重新检查来源文档有效性、版本和证据内容。
- 模型分析属于待确认分析，不代替人工核对条款。

### 4. 产品对比如何保证资料归属？

客户需求分析的产品证据阶段使用 12 字段提取协议。每个字段关联文档、版本、页码、切片和逐字摘录。

同一产品的片段先去重；跨文档归并时要求正式名称和公司信息都有依据且一致。出现冲突时保留冲突值和出处，不强行合并。至少两项正式身份可确认时才展示产品对比；否则展示候选资料核验，不做产品排名。

### 5. Agent 如何评估？

项目把“技术运行成功”和“业务任务正确”分开：

- 数据中台被动记录真实节点、工具状态、耗时、检索来源和运行终态。
- 评测中台支持 local-retrieval、observation-replay、offline-rules 等不同评测方式。
- RAG 指标包括 Recall@K、Precision@K、Hit Rate@K、MRR 等，依赖人工标注的相关文档/切片。
- Agent 可以检查节点/工具状态和工具名称，但工具执行成功不代表最终任务正确。
- 没有足够标注或可信数据时，指标显示 UNKNOWN/null，不把未知补成 0 或 100%。

### 6. 数据安全和隐私怎么考虑？

项目当前定位是本地单用户演示：

- DeepSeek Key 只从服务端环境变量读取，不暴露给浏览器。
- 客户需求分析默认不把客户输入持久化到浏览器或知识库。
- 数据中台通过读取文件、复制到临时目录、校验 SHA-256 后再扫描副本，避免直接操作源知识库。
- 评测库、数据中台和模型评测使用独立 SQLite 存储。
- 公开源码包不包含真实数据库、客户文件、模型缓存或 API 凭据。
- 真实模型调用前需要明确确认资料外发和费用。

**不要夸大：** 目前不是企业级多租户系统，没有完整的公网身份认证和租户隔离，不能直接当作可公开部署的保险 SaaS。

## 六、常见面试追问与回答

### Q1：为什么不用一个大模型加长 Prompt，而要用 LangGraph？

一个长 Prompt 适合单轮或简单任务，但客户需求分析涉及输入校验、信息结构化、需求提取、知识检索、资料版本检查、字段提取和报告导出。它们有不同的输入输出、失败条件和跳过条件。LangGraph 可以把这些步骤拆成有状态节点，通过条件边控制执行路径，并管理超时、取消和有限重试，便于观察和测试。

### Q2：RAG 的基本流程是什么？

先解析文档并切片，再用 Embedding 把文本转成向量存储；用户提问时将问题向量化，检索相关片段，再把片段作为上下文交给模型生成回答。这个项目还保留文档版本、页码和来源，并在生成前后检查资料是否仍然有效。没有证据就提示资料不足。

### Q3：如果 RAG 检索不到，怎么排查？

我会分层检查：第一，确认用户问题是否被正确保留和结构化；第二，检查文档是否解析成功、切片是否合理；第三，确认 Embedding 模型和向量维度是否一致；第四，检查当前文档状态、版本过滤和检索策略；第五，用实际查询做测试集验证召回情况。项目中还增加了受限关键词候选，解决明确产品名称或责任词被宽泛类别查询遗漏的问题。不能为了提高命中率就随意降低阈值，因为误召回也会带来错误依据。

### Q4：如何避免把检索相似的内容当成正确答案？

相似度只负责召回候选，不负责判断业务事实。最终字段必须回到原文核对，并绑定文档版本、页码和片段。冲突时保留冲突，不足时标记未知。检索命中不等于模型已经采用该引用，更不等于保险结论正确。

### Q5：工具调用如何控制风险？

工具只在服务端执行，使用白名单和参数校验，不向模型开放任意 Shell、SQL 或文件路径能力。每个工具有明确输入输出和执行状态，工作流还限制步数、时间和重试次数。取消后不启动后续工具。

### Q6：为什么要做数据中台和评测中台？

数据中台关注“数据本身是否可靠”：文档、版本、切片、向量、质量检查和快照。评测中台关注“系统表现如何”：RAG 命中情况、Agent 节点和工具运行情况、离线规则评分与人工复核。两者解决的问题不同，不能把数据质量检查当成模型答案评测。

### Q7：337 项测试和 132 项 Playwright 测试说明什么？

它们说明公开发布包在对应隔离测试范围内通过了自动化检查：337 项 node:test 和 132 项桌面/移动端 Playwright 测试。但模型请求使用 Mock，RAG 测试包含真实本地 Embedding 与检索；这不能证明真实付费 DeepSeek 的完整业务质量，也不能证明公网部署安全。

### Q8：现在能不能直接部署给保险公司客户使用？

不能直接这样承诺。当前是本地单用户演示版本。面向真实客户部署前，还需要身份认证、租户隔离、权限体系、限流和配额、日志审计、数据加密与脱敏、备份恢复演练、真实模型质量评测以及业务合规审核。

### Q9：如果模型调用超时或用户取消怎么办？

工作流把取消和超时作为明确终态处理，停止后续节点或案例执行，保留可确认的部分结果和失败原因。真实模型调用还要考虑请求发出后可能已经计费，因此不能把本地取消等同于供应商没有计费，也不对不确定失败自动重放。

### Q10：你认为项目最重要的设计原则是什么？

**把模型输出当作需要核验的候选结果，而不是天然可信的事实。** 通过状态编排、来源证据、版本检查、未知状态和人工复核，让系统在资料不足时能够明确停下来。

## 七、一个真实项目问题：如何讲清楚“发现问题—定位—修复”

可以使用客户需求检索优化作为案例：

**背景：** 客户在自然语言中明确写出产品名称或责任词，但原入口主要使用类别模板构建向量查询，可能丢失原始产品名称；宽泛责任词也可能低于原有校准阈值。

**定位：** 问题不一定是 Embedding 模型不准确，也可能是查询构造阶段已经丢失了关键信息。需要同时检查原始需求、检索计划、向量候选和当前有效文档。

**处理：**

1. 保留客户明确提出的完整需求。
2. 通过受限查询计划复用原向量检索。
3. 增加文档名、责任词和字段词的只读关键词候选。
4. 两路候选排名融合、去重，并限制最多 3 份候选文档和 5 个片段。
5. 重新检查文档当前版本和有效状态。
6. 不降低共享向量阈值，不伪造关键词余弦分数。

**结果边界：** 相关专项验证覆盖完整文件名、部分名称、责任词和不存在的显式产品名称；一次专项真实 DeepSeek 产品摘录验证了 2 个片段和 4 个字段的原文核验。但不能把这项专项验证说成整个客户分析流程已完成全程真实模型验收。

## 八、售前解决方案表达：从技术讲到业务价值

面试 AI 售前解决方案顾问时，除了讲技术，还要把业务问题翻译成方案。

| 客户可能遇到的问题 | 对应方案能力 | 可表达的价值 |
| --- | --- | --- |
| 保险资料多，人工查找费时 | 私有知识库、文档解析、RAG 检索 | 缩短资料定位和整理路径 |
| 同一问题需要跨多份资料核对 | Agent 工作流、字段提取、证据关联 | 将多步骤工作标准化、可追溯 |
| 模型回答缺少依据 | 原文引用、版本核验、未知状态 | 方便人工复核，降低无依据结论风险 |
| 业务结果需要交付 | 结构化报告、Word/PDF 导出 | 减少重复整理工作 |
| 难以判断系统是否可靠 | 数据中台、评测中台、人工复核 | 让运行和质量问题更容易定位 |

**推荐表达方式：**

先问清楚客户的资料类型、用户角色、数据权限、业务流程、准确性要求和部署环境，再给出分阶段方案。不要一开始就承诺“准确率 100%”“完全替代人工”或“开箱即用支持多租户”。
